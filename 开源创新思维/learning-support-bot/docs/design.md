# 设计说明 · 学习支持助手 MVP

## 1. 项目背景

**客户**：北辰在线学院（在线教育机构）
**场景**：学习支持与辅导协作
**核心痛点**：学生问题散在微信群、作业评论区、私信等多渠道，助教容易漏看连续求助，重复回答相似问题，学习掉队信号发现太晚——"学习掉队以后才收到提醒"。

**关键角色**：
| 角色 | 职责 |
|---|---|
| 林亦舟（助教） | 一线答疑，问题的主要处理人 |
| 顾明岚（学习服务主任） | 管理者，对响应时长、满意度负责 |
| 唐映秋（课程运营员） | 课程内容运营 |
| 秦芮（学习平台工程师） | 平台技术支持 |
| 傅景（教育数据专员） | 学习数据分析 |
| 叶书（课程讲师） | 主讲老师 |

## 2. 设计目标

用最小闭环验证一个假设：**AI 预处理 + 人工复核**能否在保证答疑质量的前提下，把助教从重复劳动中解放出来，让掉队信号更早被发现。

核心指标（基线待采集）：
- 平均响应时长
- 问题一次解决率
- 助教人均处理量
- 人工复核率
- 学生满意度（CSAT）

## 3. 系统流程

```
学生提问（多渠道汇聚）
    ↓
① 意图分类（AI/规则）
    ↓
② 置信度判断
    ├── 高置信 + 低风险 → AI 直接生成初答 → 发给学生（助教事后抽检）
    ├── 低置信 / 高风险 → 转人工助教
    └── 技术问题 → 转平台技术支持
    ↓
③ 人工复核与补充回答
    ↓
④ 问答留痕 → 沉淀知识库
```

## 4. 人工责任边界（不可自动做的事）

参考 FDE 训练中心的"人工兜底回路"原则，以下动作**必须人工确认**：

1. **学习掉队预警**：涉及学生学习状态判断，必须专属助教跟进，不能 AI 自动发通知；
2. **正式结论答复**：涉及成绩、考试、退费等正式承诺，必须具名人工确认；
3. **敏感信息处理**：学生个人信息、隐私数据，AI 不得自动外传；
4. **写回外部系统**：任何对学生账户、课程状态的写操作，人工确认后执行。

## 5. MVP 范围

本 MVP 只做最核心的"单问题处理链路"：
- ✅ 文本输入问题
- ✅ 规则版分类器（5 类）
- ✅ 模板版初答草稿
- ✅ 规则版转人工路由
- ✅ Web 演示页面
- ✅ 问答留痕（JSONL）

**不做**（后续迭代）：
- ❌ 接入真实大模型 API（当前用规则/模板模拟）
- ❌ 多渠道消息接入（微信群、作业评论区）
- ❌ 知识库检索增强（RAG）
- ❌ 学生端 App / 助教工作台完整界面
- ❌ 数据看板

## 6. 技术选型

- **Web 框架**：Flask（轻量，够 Demo 用）
- **分类器**：关键词规则（MVP 阶段可解释、零成本、易调试；后续可换 BERT/LLM）
- **初答生成**：模板匹配（可控、不会胡说；后续换 LLM 生成）
- **数据存储**：JSONL 日志（MVP 阶段无需数据库；后续换 PostgreSQL）
- **配置**：YAML（规则、阈值可调，无需改代码）

## 7. 后续演进路线

1. **v0.2**：接入 LLM API（如 DeepSeek），把规则分类换成语义分类，初答换成 LLM 生成；
2. **v0.3**：接 RAG 知识库，让初答基于课程资料回答，降低幻觉；
3. **v0.4**：接多渠道消息（企业微信 / 微信群机器人 / 作业系统 webhook）；
4. **v0.5**：助教工作台（队列、认领、回复、抽检）+ 数据看板。
